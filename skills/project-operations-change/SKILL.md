# 项目运维与变更阶段

用于处理上线后的发布、运维、故障、配置和需求变更，并保持项目资料可追踪。

## 输入

- `docs/06-release/`
- `docs/07-operations/`
- `docs/08-decisions/`
- `docs/01-requirements/CHANGE_REQUESTS.md`
- `docs/01-requirements/REQUIREMENT_TRACEABILITY.md`
- `src/`
- `tests/`

## 工作流

1. 明确变更类型：需求变更、缺陷修复、配置变更、部署变更、数据迁移或故障处理。
2. 做影响分析：需求、设计、代码、测试、验收、发布、运维是否受影响。
3. 更新变更记录和需求追踪矩阵。
4. 涉及发布时补充发布说明、部署步骤、回滚方案和验证步骤。
5. 涉及故障时记录现象、影响范围、根因、修复、验证和预防措施。
6. 涉及数据或配置迁移时写明备份、回滚、灰度和监控策略。
7. 阶段结束时记录当前状态、关键决策、验证结果和下一步动作。

## 输出

- 更新 `docs/06-release/`
- 更新 `docs/07-operations/`
- 更新 `docs/01-requirements/CHANGE_REQUESTS.md`
- 必要时新增 ADR 或运维事件记录

## 质量门槛

- 每个变更都有影响分析和验证方式。
- 发布必须有回滚或补救方案。
- 运维文档必须能让后续 AI 理解当前运行状态。
- 事故复盘不能只写现象，要记录根因和预防措施。
- AI 应用运维应包含配置、监控、成本、限流、安全和评估样本维护。
- 外部集成应写清认证、超时、错误结构、重试和降级策略。
