# 项目开发阶段

用于在已有需求和设计约束下实现功能，并保持代码、测试和文档同步。

## 输入

- `docs/01-requirements/`
- `docs/02-design/`
- `docs/03-development/DEVELOPMENT_GUIDE.md`
- `docs/03-development/CODING_STANDARDS.md`
- `src/`
- `tests/`

## 工作流

1. 先确认关联需求编号和设计文档，不清楚时补充待确认问题。
2. 阅读现有源码结构、测试结构和开发规范，优先沿用项目已有风格。
3. 明确输入、处理、输出，保持模块边界、状态变化和错误处理清晰。
4. 小步实现功能，避免一次性大改；先能运行，再优化结构，最后考虑性能。
5. 新增或修改测试，覆盖主路径、边界、失败路径和回归风险。
6. 涉及接口、数据模型、配置、部署或运维行为时，同步更新文档。
7. 运行可用的格式化、类型检查、测试或构建命令。
8. 对生成代码进行代码审查，检查安全、回归、测试缺口和维护性。

## 输出

- 更新 `src/`
- 更新 `tests/`
- 必要时更新 `docs/02-design/`、`docs/03-development/`、`docs/04-testing/`

## 质量门槛

- 代码行为能追溯到需求或明确的用户请求。
- 新增公共行为应有测试或明确说明无法测试的原因。
- 不引入无依据的大型抽象。
- 不删除未知用途代码或文档。
- 命名应语义化，函数偏动词，变量偏名词，避免无意义缩写。
- 注释解释“为什么”，不要重复描述代码正在做什么。
- 所有敏感配置应使用环境变量或配置文件示例，不写入真实密钥。
