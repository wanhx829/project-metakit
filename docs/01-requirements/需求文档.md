2项目概述
2.1目标
本项目的总体目标是围绕三大核心能力域实施系统化升级，形成可复制、可治理、可观测、可恢复的平台能力体系，支撑多现场稳定交付。通过本次升级，平台将具备更强的环境适应能力、更高的发布效率和更完善的运行治理能力，为 2026 年交付规模增长与运行环境复杂度提升提供坚实的底座支撑。
底座兼容与集群性能优化方面，项目将完成 Rocky 10.1、麒麟 V11、腾讯云 Linux V4 等目标操作系统的深度适配，充分利用新版本操作系统的性能优化、安全更新及可维护性提升等特性，增强平台底座的稳定性与安全性。同时，治理 Kubernetes 底座网络与性能问题，解决 iptables 规则链膨胀导致的性能下降问题，修复 VIP 无法访问 NodePort 的异常场景。此外，对 Bitnami 闭源依赖进行替代，通过自研封装或第三方方案实现可持续维护，消除组件供应不可控风险。
发布与流水线能力升级方面，项目将拆分云端打包系统并前置关键逻辑，缩小首次部署包体积，缩短首装时间，提升现场交付效率。优化服务发布编排，支持微服务优雅上下线，通过流量摘除、连接排空、健康检查等机制保证业务无感知，降低发布波动并提升切换可控性。支持 PDM 非功能模块的定制流水线发布能力，满足差异化交付场景需要。优化流水线打包逻辑，降低磁盘资源开销，提升构建与交付效率。
安全治理与运维策略配置方面，项目将提供熔断、限流、降级的运维配置界面，支撑运行治理策略配置、审计与回退，增强平台对微服务运行态的治理能力。提供灰度发布的运维配置界面，支持灰度规则配置、分批控制、状态观测与回退能力，通过逐步放量的方式降低发布风险，提高发布过程的灵活性和控制力。
2.2系统范围
本项目在现有 EmpowerX 自动化运维平台基础上进行升级，不改变平台整体架构，围绕底座兼容与集群性能优化、发布与流水线能力升级、安全治理与运维策略配置三大能力域，各能力域的功能范围如下：
1、底座兼容与集群性能优化
完成 Rocky 10.1、麒麟 v11、腾讯云 Linux V4、统信OS 等目标 OS 的深度适配，充分利用新版本操作系统的性能优化、安全更新及可维护性提升等特性，增强平台底座的稳定性与安全性，降低因底层系统漏洞引发的运行风险。
将适配结果固化为兼容矩阵与安装基线，形成标准化的环境准入与验证规范，丰富底座适配矩阵，提升对多样化现场环境的覆盖能力。
治理 Kubernetes 底座网络与性能问题，解决 iptables 性能下降和 VIP 无法访问 NodePort 的问题。
对 Bitnami 闭源依赖进行替代，通过自研封装或第三方方案实现可持续维护。
2、发布与流水线能力升级
拆分自动化运维云端打包系统并前置关键逻辑，缩小首次部署包体积，缩短首装时间。
优化服务发布编排，支持微服务优雅上下线，降低发布波动并提升切换可控性。
支持 PDM 非功能模块的定制流水线发布能力，满足差异化交付场景需要。
优化流水线打包逻辑，降低磁盘资源开销，提升构建与交付效率。
3、安全治理与运维策略配置
提供对接微服务熔断、限流、降级的运维配置界面，支撑运行治理策略配置、审计与回退。
提供对接灰度发布的运维配置界面，支持灰度规则配置、分批控制、状态观测与回退能力。
2.3系统架构
2.3.1系统总体架构
EmpoworX 自动化运维平台采用云端、传输工具、运维控制台分离架构。云端负责版本管理、策略配置、质量分析和远程管控；部署端（运维控制台）负责实际的服务器部署、发布执行、监控采集和故障处置。
平台基于 Kubernetes 容器编排，使用 Helm 进行组件管理，通过 Nacos 实现配置中心和服务注册，采用 Sentinel 实现流量治理。
2.3.2本系统架构
本项目在既有自动化运维平台基础上进行增强，覆盖云端、现场端、流水线、运维控制台、可观测组件、治理策略。

3.2底座系统版本升级
3.2.1功能描述
针对 Rocky 10.1、Kylin V11、TencentOS 4.4、统信UOS V20 操作系统进行深度适配及调优，验证新 OS 环境下自动化运维平台、Kubernetes 底座、中间件、可观测组件和发布部署脚本的兼容性、稳定性和性能表现。系统应保留 Rocky 9.4、Kylin V10、OpenEuler 22.03 及新增的统信UOS V20低内核系统部署打包逻辑作为过渡方案。新项目现场默认以新系统(Rocky 10.1、Kylin V11、TencentOS 4.4)底座。同时需要对 Kubernetes、CNI、监控、日志等底座组件进行版本升级，并将部署包按“系统+版本”维度拆分，缩减初次安装包体积和现场首装时间。
3.2.2权限描述

普通用户  项目资源评估、项目实施/模块登记。

3.9优雅上下线
3.9.1功能描述
优雅上下线用于解决服务发布、重启、扩缩容、临时维护过程中直接停止实例导致的请求失败、任务重复执行、消息丢失或流量瞬断问题。功能分为“服务优雅下线”和“服务优雅上线”两个方向：下线时按顺序完成入口流量摘除、Nacos 注册状态变更、XXL-Job 任务暂停、MQ Producer/Consumer 绑定停止、连接排空和实例停止；上线时按顺序完成实例启动、基础健康检查、Nacos 注册恢复、MQ 绑定恢复、XXL-Job 任务恢复、流量接入和发布后观测。
本功能需要和发布编排能力联动。发布编排调用该能力时，应对每个实例记录上下线状态、执行耗时、失败原因和回滚动作，确保发布过程可观测、可审计、可回退。

3.9.3前置条件
服务已接入 Nacos 注册发现，且支持通过运维平台或内部接口控制注册/摘除状态。
服务已支持优雅上下线开关 gracefulEnable；开启后需要关闭 Nacos 和 XXL-Job 默认自动注册机制，改由自动化运维平台编排控制。
目标服务具备健康检查接口，至少能返回进程存活、依赖组件连通性和业务基础可用状态。

使用 MQ 的服务需支持 Producer/Consumer 绑定停止和恢复；关闭 Consumer 前需完成在途消息处理或确认补偿策略。

3.9.5业务说明
3.9.5.1服务优雅下线

服务下线用于发布替换、实例维护、故障隔离和容量调整等场景。
具体需求如下：
系统发布后平台强制开启优雅上下线配置。
运维控制台提供优雅上下线全局开关配置，支持全局开启或者关闭。
运维控制台发起下线操作，然后调用kebea通信程序执行服务优雅下线。
系统接收到下线指令后，先检查服务当前副本数、可用实例数量、目标版本和发布任务冲突情况；检查通过后，应先从入口或负载均衡侧摘除目标实例流量，再将 Nacos 中目标实例标记为不可用或注销，防止新请求继续进入。
Nacos 摘除完成后，系统应暂停该实例相关 XXL-Job 任务，停止 MQ Consumer 接收新消息，并等待存量请求、任务和在途消息处理完成。达到连接排空条件或最大等待时长后，系统方可停止旧实例并记录下线结果。
3.9.5.2服务优雅上线
服务上线用于新版本发布、回滚恢复、扩容和故障恢复等场景。
运维控制台发起下线操作，然后调用kebea通信程序执行服务优雅上线。
系统启动新实例后，先执行本地健康检查，检查进程、端口、配置、数据库、中间件和关键依赖是否正常，当前能力依赖与微服务基础平台能力。
检查通过后恢复 Nacos 注册，使服务可被发现；恢复 MQ Producer/Consumer 绑定，使消息生产和消费恢复；恢复 XXL-Job 任务调度；最后接入入口流量。
上线完成后持续观察接口成功率、错误率、响应时间和实例重启次数，观测窗口内异常则触发暂停或回滚。
3.9.5.3异常处理与回滚  
若下线阶段 Nacos 摘除失败，系统不得继续停止实例。
下线流程从调用下线开始，达到60s仍未完成时，系统按策略执行强制删除。
优雅上线先过程异常时，运维控制台记录详细异常日志，便于后续排查。
发布失败记录回传云端，有网络条件的，发送企业微信进行告警。
3.9.5.4用例场景
场景1：发布替换旧实例。运维用户发布新版本时，系统先选择一批旧实例进入下线流程，完成入口摘流、Nacos摘除、XXL-Job暂停、MQ Consumer停止和连接排空后停止旧实例；随后启动新版本实例，健康检查通过后恢复注册和接流。
场景2：上线健康检查失败。新实例启动后数据库连接检查失败，系统阻止 Nacos 注册和入口接流，发布任务进入失败状态；
场景3：MQ 消费者安全下线。服务实例存在正在处理的消息，系统停止新消息拉取并等待在途消息确认；超过连接排空时长仍未完成时，根据失败处理策略进入强制下线。

平均请求量(个/秒)  按时间窗口统计接口平均请求量 Top5。  识别高频接口和容量压力。
平均响应时间(ms)  按时间窗口统计接口平均 RT Top5。  识别慢接口。
P99响应时间(ms)  统计接口长尾响应时间 Top5。  识别偶发高延迟接口。
平均错误率(%)  统计接口平均错误率 Top5。  识别异常率高接口。
最近20条接口告警日志  展示最新告警记录。  支持告警追溯和处置复盘。

3.11.5.4降级与回退处理
降级用于服务不可用或熔断触发时返回简化响应或备用结果，维持基本功能。
降级响应应支持统一错误码、提示信息、默认数据和扩展字段。
自动化运维平台负责参数校验、冲突提示和高风险识别，微服务基础平台负责规则保存、生效和回退；
保存失败时不得覆盖当前生效规则。
3.11.5.5用例场景
场景1：配置单服务QPS限流。运维用户选择订单创建接口，配置单服务QPS=1000，流控效果为快速失败。自动化运维平台校验通过后保存规则，页面展示QPS、限流次数，并将QPS结果回传云端。
场景2：维护手动熔断配置。运维用户进入服务详情页面，点击“熔断配置”打开“熔断管控列表”，新增上游模块 syncplant-business-eam，设置“允许上游调用”开关并保存；系统校验权限后写入熔断管控配置，页面展示生效状态并记录操作审计。
场景3：执行临时熔断。生产环境发现某上游模块持续触发异常调用，项目管理员在熔断管控列表中关闭该上游模块的“允许上游调用”开关，系统保存成功后立即展示停用结果，并在审计记录中保留操作原因、操作人和TraceId。
场景4：批量启停熔断管控。运维用户选择多条上游模块记录执行批量停用，系统逐条校验权限和配置状态；部分记录保存失败时，页面展示失败明细，成功记录保持已生效状态。
场景5：风险接口性能概览。运维用户查看近1小时性能概览，发现 P99 响应时间 Top5 中某接口异常升高，进入接口限流弹窗配置临时单服务QPS限流并记录处置结果。

3.12灰度发布
3.12.1功能描述
灰度发布用于在新旧版本同时存在时，通过规则配置将部分流量导向灰度版本，经过观测验证后逐步放量。本项目不在自动化运维平台重新实现客户端负载均衡或灰度路由底座，而是在自动化运维平台提供灰度发布配置页面，复用微服务基础平台已实现的 appVersion、数据标透传、Nacos 灰度配置和 syncplant-starter-loadbalancer 能力。
自动化运维平台负责灰度配置页面、规则参数校验、K8S集成阿里调度器、二阶段暂停和回退操作；微服务侧负责灰度路由、数据标透传和规则生效。
具体需求如下：
用户点击“部署”打开版本切换弹窗，可选择目标版本并在弹窗内开启灰度发布、配置灰度策略；
用户点击“详情”进入服务详情页面，查看当前服务的运行版本、灰度进度和POD版本分布；
POD节点列表应展示当前版本，便于区分稳定版本实例和灰度版本实例。
自动化运维平台应支持创建灰度规则、配置灰度策略、审批、二阶段暂停、二阶段回退以及全量发布；
微服务基础平台负责保存 Nacos 灰度规则、执行 LoadBalancer 路由、返回灰度状态和回退结果。
参考微服务高级特性，灰度策略分为按流量比例、按请求参数和按人员三类，三类策略不能同时生效，优先级为按人员 > 按请求参数 > 按流量比例。

角色  操作权限

3.12.3前置条件
K8S已具备阿里调度器控制台集成条件，自动化运维平台可提供灰度规则配置页面。
微服务侧已具备灰度发布底座能力，支持 appVersion、数据标透传、Nacos 灰度规则和 syncplant-starter-loadbalancer。
目标服务支持多版本部署，新旧版本可同时存在。

3.12.5.2灰度规则配置
以下灰度能力依赖微服务平台高级特性。
灰度策略分为按流量分配、按请求参数分配和按人员分配。
按流量分配支持配置任意比例，如 10%、20%、37%、50%、100%；100% 表示灰度流量全部进入灰度版本，不等同于关闭灰度。
按请求参数分配支持来源 IP、请求头参数、URL 路径等条件。
按人员分配支持人员编码，自动化运维平台负责页面配置和校验，微服务基础平台负责规则生效。
灰度策略类型
策略类型  说明  配置示例
人员灰度  指定用户或用户组进入新版本。  user-list: user001,user002
请求参数灰度  按来源IP、请求头或URL路径命中新版本。  header-map: x-gray=true

3.12.5.3灰度路由与数据标透传
所有请求应在链路中传递数据标识，灰度规则基于数据标和 appVersion 判断目标实例。
Nacos 存储灰度规则，微服务监听规则变化后由客户端 LoadBalancer 动态选择旧版本或新版本实例。
上述路由执行能力由微服务基础平台提供，自动化运维平台仅展示配置、命中结果、观测指标和回退状态。
3.12.5.4观测、放量与回退
灰度发布应按批次逐步扩大流量比例。
每个批次进入观测窗口，观测接口成功率、错误率、响应时间、QPS、实例重启次数和业务告警。
指标达标后可扩大灰度比例或全量发布；
指标不达标时应支持二阶段暂停和二阶段回退，切回稳定版本并保留灰度报告。
服务详情页面应提供灰度进度展示区，展示源版本、目标版本、当前阶段、当前比例、观测状态、预计完成时间和批次进度。
灰度过程中，页面提供“暂停”“继续”“回退”操作按钮；
暂停后保留当前流量比例和规则状态，继续后从暂停批次恢复执行，回退后将流量切回稳定版本。
3.12.5.5用例场景
场景1：按流量比例灰度。运维用户选择微服务基础平台，灰度版本为 2.0.0，批次设置为 10% -> 30% -> 100%。自动化运维平台通过K8s集成的阿里调度器控制台配置灰度规则，微服务侧将 10% 流量路由至新版本，自动化运维平台展示观测结果。
场景2：部署时开启灰度。运维用户在服务列表点击“部署”，系统打开版本切换弹窗；用户选择目标版本 2.2.2.12-1，开启灰度发布，选择流量比例灰度并设置初始比例为10%。系统保存部署参数后，用户点击服务列表“详情”进入服务详情页面，查看“从 2.2.2.11-1 到 2.2.2.12-1”的灰度进度。
场景3：按人员灰度。项目管理员指定部分测试人员和业务代表访问新版本，其他用户仍访问稳定版本。自动化运维平台负责人员名单配置和审批记录，微服务基础平台负责人员命中和路由执行。
场景4：按请求参数灰度。运维用户按 Header 或 URL 规则将特定来源请求路由到新版本，用于验证某类业务请求链路；规则保存和命中判断由微服务基础平台完成。
场景5：灰度暂停与继续。灰度执行到30%比例后，运维人员在服务详情页面点击“暂停”，系统保持当前比例并停止继续放量；确认观测指标稳定后点击“继续”，系统按原批次计划继续执行。

4.2系统安全及保密要求
平台应遵循公司用户权限和项目权限管理要求。
