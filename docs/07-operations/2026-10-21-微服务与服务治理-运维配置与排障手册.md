## 1. 核心依赖组件健康检查命令

在执行任何微服务治理操作（优雅发布、限流、灰度）前，必须确认以下基础支撑组件正常运行：

```bash
# 1. 检查 empoworx-kubea 运行状态与端口 (默认监听端口 8080/8888)
curl -s http://127.0.0.1:8888/testapi
```

```bash
# 2. 检查 Nacos 注册中心连通性与服务列表
curl -s "http://nacos.syncplant.svc:8848/nacos/v1/ns/service/list?pageNo=1&pageSize=10"
```

```bash
# 3. 检查 Sentinel 配置组 (SENTINEL_GROUP) 的规则发布情况
curl -s "http://nacos.syncplant.svc:8848/nacos/v1/cs/configs?dataId=syncplant-business-eam-flow-rules&group=SENTINEL_GROUP"
```

```bash
# 4. 检查 InfluxDB 监控时序数据库健康检查接口
curl -s http://influxdb.syncplant.svc:8086/health
```

## 2. 关键配置参数字典

| 配置项 | 所在配置文件 / 环境变量 | 默认值 | 推荐生产值 | 作用说明 |
| :--- | :--- | :--- | :--- | :--- |
| `graceful.drain.timeout` | `base.toml` / `kubea.yaml` | `30s` | `20s` | 优雅下线等待在途请求完成的最大超时时间，超时后强制终止 |
| `graceful.warmup.duration` | `base.toml` | `60s` | `120s` | 新实例上线反向预热时长（流量按权重递增至 100%） |
| `nacos.group.sentinel` | `conf/application.toml` | `SENTINEL_GROUP` | `SENTINEL_GROUP` | Sentinel 规则在 Nacos 中存储的 Group 名称 |
| `influxdb.retention.policy` | InfluxDB Bucket 配置 | `7d` | `30d` | API 监控时序数据保留周期，防止指标占满磁盘 |
| `governance.log.audit` | `conf/app.conf` | `true` | `true` | 是否对限流、熔断、优雅重启等治理行为开启持久化审计 |

## 3. 高频故障诊断与排障指引

### 故障 1：优雅下线卡在“正在注销 Nacos”超时报错

#### 现象
控制台提示：“优雅下线任务失败：阶段 [Nacos Deregister] 超时”。

#### 排查步骤
1. 检查 Nacos 服务端是否发生 Full GC 或 Leader 重新选主；
2. 检查 `kubea` 节点到 Nacos 的网络联通性及 DNS 解析：
```bash
kubectl exec -it deployment/empoworx-kubea -n autoops-system -- ping -c 3 nacos.syncplant.svc
```
3. 查看 `empoworx-kubea` 日志：
```bash
kubectl logs -f deployment/empoworx-kubea -n autoops-system --tail=100 | grep "graceful"
```
4. **应急恢复**：若确为 Nacos 偶发抖动，可在确认业务流量低谷时，直接通过 K8s 原生命令进行单个 Pod 销毁重建：
```bash
kubectl delete pod <target-pod-name> -n <namespace> --grace-period=30
```

### 故障 2：配置了 QPS 限流规则但业务请求未被拦截（压测无 429）

#### 现象
在 API 管控页面为某接口配置了 QPS=500 限流，但压测打到 1000 QPS 依然全部穿透。

#### 排查步骤
1. **排查 Nacos 配置是否成功下发**：
   访问 Nacos 控制台，搜索 Group 为 `SENTINEL_GROUP`，检查对应 DataId `{serviceName}-flow-rules` 内容是否生成；
2. **排查网关/微服务是否开启 Sentinel 监听**：
   检查微服务日志中是否包含 `[Sentinel] Dynamic rule loaded successfully from nacos`；
3. **排查接口路由匹配规则**：
   检查 Controller 定义的 URL 是否包含路径参数（如 `/api/order/{id}`），Sentinel 默认按精准匹配，若为通配路径需确认网关是否统一转换为 URL 模式匹配；
4. **排查限流口径**：
   确认规则中的 `limitApp` 是否为 `default`（对所有上游生效），若误填了特定上游应用名，其他应用请求将不被拦截。

---

### 故障 3：手动熔断后想要一键紧急恢复

#### 应急恢复步骤
1. 若前端控制台可用：
   进入“微服务治理” -> “熔断配置”，找到被标记为“禁止”的上游模块条目，点击 `[解除熔断]` 并确认，系统将在 1 秒内推送到 Nacos；
2. 若控制台网络断开（离线应急）：
   通过 curl 直接修改或删除 Nacos 中的限流规则：
```bash
curl -X DELETE "http://nacos.syncplant.svc:8848/nacos/v1/cs/configs?dataId=syncplant-business-eam-flow-rules&group=SENTINEL_GROUP"
```
   删除后，微服务与网关将立即恢复全量放行。
