# EmpoworX 自动化运维平台 V3.0 升级项目测试方案

## 1. 测试目标

本测试方案面向当前开发节点的开发自测和测试执行，目标是基于已提交的需求文档、详细设计和开发中代码，验证 EmpoworX 自动化运维平台 V3.0 升级范围内的核心场景、异常处理、权限控制、配置生效、审计追踪和回退能力。

由于当前需求和原型仍存在不完整内容，本方案按“场景用例优先”编写：优先覆盖用户可执行链路和高风险运维动作；对尚未明确的字段、接口细节和验收阈值，在待确认问题中标记，不将推断写成已确认事实。

## 3. 不测试范围

- 不验证未提供原型、接口或实现入口的纯视觉细节。
- 不对第三方组件自身功能做完整验证，例如 Kubernetes、Nacos、Sentinel、InfluxDB、Helm、KubeVirt 的原生能力，只验证平台集成结果。
- 不对未纳入本次 V3.0 升级范围的既有自动化运维平台功能做全量回归，仅覆盖受影响链路。
- 不替代生产容量规划和现场专项压测；本方案只定义可用于开发自测和测试执行的验证场景。

## 7. 测试策略

| 测试类型 | 目标 | 方法 | 通过标准 |
| --- | --- | --- | --- |
| 功能测试 | 验证核心业务链路可用 | 按功能编号执行场景用例，覆盖新增、编辑、查询、删除、执行、查看状态 | 预期页面、接口、任务状态和数据结果一致 |
| 接口测试 | 验证后端接口参数校验、响应结构和错误处理 | 使用页面或接口工具调用设计文档中的 API，检查 R 结构、TraceId、失败阶段 | 成功响应字段完整，失败原因可定位，不产生脏数据 |
| 集成测试 | 验证平台与 Kubernetes、Nacos、Sentinel、InfluxDB、Jenkins、告警平台联动 | 使用真实或联调依赖，检查配置下发、指标读取、任务回调和审计 | 外部依赖状态与平台状态一致 |
| 权限测试 | 防止越权执行高风险运维动作 | 使用不同角色执行查询、配置、部署、回退、删除等操作 | 无权限操作被阻止，并有明确提示和审计 |
| 异常测试 | 验证失败时不破坏当前稳定状态 | 注入依赖失败、参数非法、资源不足、网络异常、部分批量失败 | 原配置或运行版本不被覆盖，失败阶段和原因明确 |
| 边界测试 | 验证阈值、长度、比例、分页和时间范围边界 | 使用空值、重复值、超长值、0/1/100/101、最大分页等数据 | 合法边界可通过，非法边界被校验 |
| 回归测试 | 验证既有部署、发布、监控、模块管理不被破坏 | 选取受影响旧链路做冒烟和关键路径回归 | 旧功能路径可用，兼容旧 OS 和旧部署方式 |
| 性能测试 | 验证关键非功能目标 | 对比首包体积/首装时间，查询分钟级聚合指标，执行灰度和限流压测 | 达到已确认阈值；未确认阈值记录测试数据 |
| 安全测试 | 验证敏感信息、弱密码、包安全和审计 | 检查部署包目录穿越、敏感参数脱敏、Nacos 弱口令、二次确认 | 敏感信息不落库不进日志，高风险操作可追踪 |

## 8. 准入准出标准

### 准入标准

- 需求文档、详细设计和当前迭代原型已放入项目目录，功能范围已由项目负责人确认或标记 TODO。
- 开发提供可部署版本、接口地址、初始账号、测试环境访问方式和必要外部依赖。
- 对应功能的配置项、测试数据、测试包、测试服务或 Mock 数据已准备。
- 高风险操作具备可回滚环境，避免在不可恢复环境执行破坏性用例。

### 准出标准

- P0/P1 场景用例执行完成，阻塞和严重缺陷已修复并回归通过。
- 配置下发、发布、回退、删除、卸载等高风险操作均验证审计记录。
- 已执行用例具备证据：页面截图、接口响应、任务日志、数据库/配置快照或 Kubernetes 状态。
- 未执行、阻塞、不适用用例已说明原因和风险。
- 已知遗留问题有负责人、影响范围、规避方案或上线决策记录。

## 9. 风险和应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 需求和原型仍在变化 | 用例可能与实际实现不一致 | 用例按场景和需求编号组织，执行前根据实际页面补充字段和入口 |
| 多 OS、多架构环境资源不足 | BASE-01 无法全矩阵执行 | 先执行代表性矩阵，缺失组合列为阻塞或待补测 |
| Nacos/Sentinel/InfluxDB/告警平台依赖不稳定 | API 管控、限流熔断、灰度观测无法完整验证 | 准备 Mock/历史指标数据，同时记录真实联调结果 |
| 第三方应用包规范未最终确认 | GOV-05 包校验用例可能需调整 | 以设计文档的 deploy.json 和标准脚本约束为准，变更后同步更新用例 |
| 性能目标缺少明确基线 | PERF-01/PERF-02 难以判断是否达标 | 先记录优化前后数据，待项目确认基线和阈值后补充判定 |
| 部分源码仍在开发中 | 自动化测试命令可能无法执行或失败 | 本阶段以手工场景用例为主，开发完成后补充接口/自动化测试 |
