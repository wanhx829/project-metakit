2.4软件功能描述
EmpoworX自动化运维平台V3.0升级项目围绕底座兼容与集群性能优化、发布与流水线能力升级、安全治理与运维策略配置三大功能域建设，功能范围以需求规格说明书中的功能需求总表为准。
1.底座兼容与集群性能优化
主要提升平台对新底座系统和默认中间件部署方式的适配能力。底座系统版本升级支持 Rocky 10.1、Kylin V11、TencentOS 4.4 等系统适配，并维护系统版本、CPU架构、Kubernetes组件和底座组件的兼容关系，支持验证结果录入和按“系统+版本”拆分部署包。
Bitnami闭源依赖替代用于将默认中间件由 Bitnami 容器化镜像方案调整为基于官方源文件编译的二进制部署方案，维护中间件二进制清单、版本、校验值和验证结果，降低闭源依赖带来的交付风险。
2.发布与流水线能力升级
主要优化云端打包、模块管理和流水线资源治理能力。云端打包系统拆分与优化用于前置依赖分析、环境检测、配置渲染等逻辑，生成最小首包和按需组件包，并支持打包进度、日志、制品目录和部署端版本选择。
中间件模块化管理用于支持 xxl-job 等中间件类型模块纳入微服务模块管理，维护模块信息、脚本、构建计划、产物信息和发布版本。流水线磁盘资源优化用于对构建缓存、临时文件、历史制品和日志进行统计、预警、清理前预览、安全清理和操作记录，降低磁盘占满风险。
3.安全治理与运维策略配置
主要提升服务发布、接口治理、流量治理和第三方应用部署过程的安全性与可追溯性。优雅上下线用于在服务部署和下线过程中联动 Nacos、XXL-Job、MQ绑定、健康检查和连接排空，降低发布过程中的流量损失。
API管控用于展示平台扫描接口清单和 InfluxDB 指标数据，支持接口查询、监控开关、SLA指标展示以及限流、趋势查看入口。限流、熔断降级用于支持接口QPS限流和服务详情中的熔断管控，按上游模块维护是否禁止上游调用，并在禁止时填写和展示禁止原因。
第三方应用部署用于支持非平台内置应用完成镜像上传、Helm包上传、部署参数配置、部署执行和状态查看，并展示Release、Pod、Service、Event等部署状态和审计记录。

3.3非功能性需求 
云端系统拆分与优化
针对新版底座适配、组件版本升级和中间件部署方式调整，对云端打包系统进行拆分与优化。改造后，云端不再按单一全量包处理所有部署场景，而是按照新旧版本、操作系统、CPU 架构和部署模式生成对应制品，减少无关资源进入首包，降低现场首次部署的包体积和安装耗时。
改造重点解决新旧底座混合维护成本高、离线资源包过大、系统差异发现较晚的问题。旧版系统继续保留过渡部署能力，新版系统独立维护部署脚本和离线资源，二者通过版本标识进行隔离，避免新版组件、脚本或配置变更影响过渡项目。
核心原则
?不破坏原有系统适配版本：保留 Rocky 9.4、Kylin V10、OpenEuler 22.03 等过渡版本部署能力，新版底座调整不得影响旧版部署链路。
?新旧版本隔离：以版本标识区分新版和过渡版本，部署脚本、离线资源、组件清单和打包策略按版本分别维护，原则上过渡版本不再更新。
?首包最小化：将系统相关资源、公共资源和可选组件拆分管理，首次部署包仅包含启动和环境初始化所需内容，其他组件按需进入对应资源包。
?前置校验：正式部署前完成系统版本、安装级别、CPU 架构匹配检查，尽早发现不兼容配置。
?兼容现有流程：保留现有传输工具和部署入口，主要调整云端打包逻辑、资源目录和部署脚本来源，最小化修改风险。

部署脚本
?以当前生产环境 devops_v2 分支作为旧版系统过渡基线。该分支原则上不再承接新版底座能力，仅保留纯 Kubernetes 容器化环境的部署能力，用于 Rocky 9.4、Kylin V10、OpenEuler 22.03 等过渡版本。
?主线分支面向新版底座持续演进，包含 Kubernetes、containerd、Cilium 等组件升级，内核参数和系统参数调整，中间件部署方式调整，以及自动化脚本重写。新版中间件以云端部署包形式归档，并通过传输工具下发到现场执行安装。
云端资源
?云端新增过渡脚本目录，保留 devops_v2 分支部署脚本作为过渡版本基线。离线资源包按 stable、legacy 等目录拆分，stable 用于新版底座，legacy 用于过渡版本。
?打包时，云端根据项目的版本模式、目标系统、CPU 架构和 legacy 标识选择资源目录，生成对应部署包。新版部署包只包含目标系统所需资源；旧版部署包继续沿用原有容器化资源，避免新版二进制或 RPM 制品进入过渡版本部署包。
闭源中间件替代
功能描述
针对Bitnami 镜像闭源及收费风险，将新部署现场的中间件交付方式从 Bitnami 容器镜像切换为官方 RPM、源码编译或官方二进制制品。Redis 采用源码编译；MySQL、MinIO、InfluxDB 等组件优先使用官方 RPM 制作离线 RPM 包，无官方 RPM 时现场编译，无法编译或官方推荐二进制运行时使用官方二进制。Nacos、Xxl-job-admin 保留容器化部署。
核心原则
?前端固定：新版页面由系统自动展示预设部署方式，不允许用户手动切换部署形态。
?制品来源可控：制品必须来自官方 RPM、官方源码包、官方二进制包或经过验证的内部镜像。
?二进制优先、镜像兼容：优先采用 RPM、源码编译或官方二进制方式；存在操作系统兼容风险时，允许使用容器镜像部署。
?运行方式统一：RPM、源码编译及二进制部署的中间件尽可能由 systemd 管理，容器化中间件沿用 Kubernetes 管理。
?兼容过渡版本：旧版底座沿用现有容器化部署逻辑，新版底座启用闭源中间件替代及混合部署策略。
改造方案
在新版中间件固定模式下，系统不再开放中间件部署形态自由选择，由平台按照预设规则自动确定各中间件部署方式。其中 Nacos、Xxl-job-admin、Seata保留容器化部署方式，其他中间件优先采用官方 RPM、官方二进制包或源码编译方式进行部署运行。
涉及中间件范围包括：MySQL、Redis、MongoDB、RabbitMQ、InfluxDB、MinIO、Nacos、Xxl-job-admin、Seata。
?新版中间件页面采用固定模式，仅展示平台确定后的部署方式，不再允许用户手动选择单机、集群或自定义部署模式。
?Nacos、Xxl-job-admin、Seata保留容器化部署，保持现有注册配置中心、任务调度、熔断能力稳定。
?Redis 采用源码编译方式生成可部署制品。
?MySQL、MinIO、InfluxDB、MongoDB、RabbitMQ 等中间件优先使用官方 RPM 制作离线安装包。
?无官方 RPM 或 RPM 不满足目标系统适配要求时，采用现场源码编译方式生成安装制品。
?无源码编译条件，或官方推荐以二进制方式运行时，采用官方二进制文件直接运行。
?RPM、源码编译或二进制制品与目标操作系统存在兼容风险时，改用经过验证的容器镜像，形成二进制与容器镜像混合部署。
?对需要保持固定 IP:Port 的容器化中间件，可采用 HostNetwork，并结合固定节点或节点亲和性保持访问地址稳定。
?使用 HostNetwork 前应校验宿主机端口占用情况。
?二进制或 RPM 安装后的中间件，尽可能统一使用 systemd 进行运行托管。
